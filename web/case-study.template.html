01The result

Ahead of the naive guess at every range, by less than the backtest said

Live MAE below persistence at {{LIVE_AHEAD}}/{{N_H}} horizons, {{LIVE_RANKED}} of them past the 200-forecast gate

{{LIVE_AHEAD}}/{{N_H}}

forecast ranges where APAW's real, made-in-advance forecasts beat "tomorrow looks like today".

Every forecast is saved the moment it is made, with the exact inputs it saw, and only checked once its day actually arrives. Nothing is ever re-scored with hindsight. The comparison is always the same dumb guess: the level will not move.

Each forecast is written to eval/predictions.csv at issue time and scored into eval/error_log.csv once the target date is observed. The baseline is persistence (ΔRWL = 0); drift is scored too and is never the stronger baseline here.

The gap is smallest one day ahead: {{H1_MODEL}} m against {{H1_PERS}} m, about {{H1_GAIN}}% better, on {{H1_N}} forecasts. One day out, a reservoir mostly moves because operators open or close the gates, and nothing APAW can see tells it when that will happen.

02The data that did not exist

PAGASA shows today and yesterday, then the reading is gone

No archive upstream, so the collector is the dataset

There was no history to download. PAGASA's flood page lists each dam's level for today and yesterday only. So the first thing APAW does, twice a day on GitHub's free servers, is save that table. A missed run is a reading lost for good, which is why saving happens before any forecasting, and the save runs even if the model crashes.

The /flood page is the only source and keeps no archive. A GitHub Actions cron runs at 08:30 and 14:30 PHT; the scrape step runs before the model and the commit step runs if: always(), so a modelling bug can never cost the one input that cannot be re-fetched. A sparse seed came from Wayback snapshots (166 dates over five years).

03How it learns

Predict, wait, check, learn, in that order, forever

Prequential evaluation: predict_one, then learn_one, in strict date order

Most models are trained once and frozen. APAW never stops training. When a day's real level arrives, it first checks the forecasts it made for that day, and only then learns from the answer. It can never peek.

The model state is never refit from scratch. On a cache miss it is rebuilt by replaying the committed history through the same predict-then-learn pass, so the rebuilt state equals the live one. Features at issue time use observations up to t and the rain forecast archived at the lead time that would have been available; tests pin that no backward window reads t+1.

04Choosing the model

{{SEARCH_TOTAL}} designs tried, with the last months locked away

Ranked on dev only; the holdout after {{SPLIT}} was scored once

Try enough designs against the same test and one will look great by luck. So the calendar was cut in two before the search started. Designs were only compared on the older dates, and the single winner met the newer dates exactly once.

eval/experiment.py ran three sweeps ({{SWEEPS}} = {{SEARCH_TOTAL}} configurations) over River estimators, feature sets, pooling, target scaling, shrinkage and baseline blending. The ranking key is the mean ratio of model MAE to the best baseline across horizons, on dates before {{SPLIT}} only.

It barely moved on dates it had never been allowed to see. That small gap, not the win itself, is the evidence that the search found something real.

The finding was about data, not algorithms

The first design was one small model per dam per range: 63 models with 13 to 94 rows each. Pooling them into one model, with the dam and the range as inputs, gave it roughly 1,750 rows to learn from. That change did more than any choice of algorithm. Each dam's changes are rescaled first, because some dams move twelve times as much as others and would otherwise drown them out.

05Backtest versus live

The practice test flattered it

Backtest margins of {{BT_MIN}} to {{BT_MAX}}% shrink to {{LIVE_MIN}} to {{LIVE_MAX}}% live

Before going live, APAW was tested by replaying the history it could recover. That replay said it beat the naive guess by up to {{BT_MAX}}%. The real, day-by-day forecasts since then beat it by {{LIVE_MIN}} to {{LIVE_MAX}}%. Still ahead everywhere, by less. For weeks the README kept showing only the replay, because that file only updates when the replay re-runs. It now shows both.

eval/metrics.json comes from backtest.py, which only runs on a model-state cache miss, so the published scoreboard sat still while the live ledger grew. The live period is also a different era: wet-season September, with errors several times larger than the recovered history. Both tables are now rendered on every run, labelled.

06An attempt that did not ship

Three fixes for the weak one-day forecast, none good enough

Pre-registered, 5 seeds each; best was {{BEST_PCT}}% against a 3% bar

Before running anything, I wrote down what would count as a win: the one-day error had to drop at least 3%, on at least 4 of 5 repeat runs. Then I tried more trees, inputs describing how the level had trended over the last 3 and 7 days, and both. All three helped a little. None cleared the bar, so none shipped.

Rule fixed in docs/ATTEMPT_NEXT.md before the run: dev +1d MAE mean over seeds 1 to 5 at least 3% below the incumbent's, and lower on at least 4 of 5 seeds; only then open the holdout once. Candidates: 100 trees, 3 and 7 day level-trend features, both. None qualified, so the holdout stayed closed.

It also found that the published score was a lucky run

The search used one random seed throughout. Re-run on five others, the same winning model scores {{SEED_RATIO_MIN}} to {{SEED_RATIO_MAX}}, and the published {{DEV}} sits at the lucky end of that range. The seed moves the score about as much as the ideas did.

07What it cannot do

It is not a warning system

Known ceilings, and why the disclaimer is permanent

Not an official warning

APAW is an educational portfolio project. Do not use it to decide whether to evacuate. PAGASA and your local disaster risk reduction office decide what counts as a warning and when water is released.

  • It cannot see the gates. Release decisions are made by people, and they are what moves a dam most in a single day.
  • Rain is estimated around the dam, not across its whole watershed. A few sample points stand in for the real catchment shape.
  • Catchment rain is a sampled cross of points, a stand-in for real watershed polygons, marked as a deliberate shortcut in the code.
  • Older rows use rain that really fell, not rain that was forecast. The forecast archive only starts in 2025, so those rows are scored separately.
  • It says when it is guessing. Forecasts beyond anything in its history are flagged on the dashboard, not clipped, because hiding extremes would gut it exactly when it matters.
08What broke

Bugs that looked like good results

Failures that produced plausible output instead of an error

A number that leaked tomorrow

PAGASA prints one "24-hour change" per snapshot and shows it on both the today and yesterday rows. On the yesterday row it is the change into tomorrow. Taken at face value, a naive guess "predicted" the next day to within 5 cm. It is now recomputed from APAW's own series, and a test keeps it that way.

"Non-Flood Watch" contains "Flood Watch"

A simple text match turned every quiet river basin into an alarm. The negative is now tested first.

Zero meant "not published"

Some dams have no official full mark or target level, and PAGASA writes those as 0.00. Left as zero, every spill rule fired. They are now treated as missing.

One missing number blanked the dashboard

Python's JSON writer outputs a bare NaN for a missing value, which is not valid JSON, so the browser refused the whole file. Values are cleaned before writing now.

A theme switch that silently did nothing

When a visitor's system flipped between light and dark, the dashboard called code for a map that had been removed, crashed, and left every chart in the old colours. No visible error, just wrong colours. Found while building this page.

09Reproduce it

Run it yourself

No accounts or keys. The data sources are public, the forecasts come from Open-Meteo's free API, and the whole loop runs on GitHub Actions' free minutes. 

git clone https://github.com/Zeref538/apaw && cd apaw
uv sync --group dev
uv run python -m pytest -q

uv run python data/fetch_dams.py      # today's readings
uv run python data/build_table.py     # join readings and rain
uv run python eval/backtest.py        # replay history, rebuild the model
uv run python pipeline/run.py         # one full tick of the loop
uv run python web/build_case_study.py # rebuild this page from the results

Stack: Python, River (online learning), pandas, GitHub Actions twice daily, GitHub Pages. The collector last ran on {{GENERATED}}.
